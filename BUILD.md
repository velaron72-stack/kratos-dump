# Сборка и проверка KRATOS DUMP

## Состав проекта

```
core/                    ядро анализа на C++17 (библиотека kratos_core, JNI-мост, консольная утилита, тесты)
  include/kratos/        публичные заголовки; api.h — плоский C-интерфейс, которым пользуется приложение
  src/                   разбор APK и ELF, поиск функций, дизассемблирование, строки, ссылки, отчёты
  jni/                   JNI-мост (libkratos_jni.so)
  tools/kratos_cli.cpp   консольная утилита для запуска анализа на компьютере
  tests/                 набор тестов, фикстуры (tests/fixtures), тест JNI в настоящей JVM
app/                     приложение для Android (Kotlin, обычные View без AndroidX)
scripts/                 загрузка закреплённых зависимостей, генерация фикстур и лицензий, проверка JNI-имён
third_party/             исходники зависимостей (см. DEPENDENCIES.md)
.github/workflows/       сборка и проверка в GitHub Actions
```

## Что нужно

Для ядра и тестов на компьютере: компилятор C++17 (GCC или Clang), CMake 3.18 или новее, Ninja, Python 3. Для теста JNI дополнительно JDK 17 или новее (нужен `javac`).

Для APK: JDK 17, Android SDK (platform 34, build-tools 34.0.0), NDK 27.2.12479018, CMake 3.22.1 из Android SDK. Gradle скачивается обёрткой `gradlew` (версия 8.10.2). Android Gradle Plugin 8.7.3 и плагин Kotlin 2.0.21 скачиваются с Google Maven и Maven Central при первой сборке.

## Исходники зависимостей

В архиве проекта каталог `third_party/` уже заполнен рабочими деревьями четырёх используемых компонентов (zlib, zstd, Capstone, ELFIO) на закреплённых коммитах, без истории git. Больше ничего скачивать не нужно. LIEF и Unicorn в архив не вошли (в сборку они не входят, а вместе весили бы больше 30 МБ).

Если каталог нужно восстановить (например, после клонирования репозитория без него) или нужна история git, выполните:

```
scripts/fetch_third_party.sh            # неглубокие клоны закреплённых тегов
scripts/fetch_third_party.sh --full     # с полной историей
scripts/fetch_third_party.sh --reference  # дополнительно LIEF и Unicorn (в сборку не входят)
```

Скрипт завершается с ошибкой, если коммит не совпал с закреплённым. GitHub Actions использует именно скрипт. Путь «чистый клон репозитория, скрипт, сборка, `ctest`» проверен в среде разработки.

## Ядро и тесты на компьютере

```
cmake -S core -B build/core -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build/core
ctest --test-dir build/core --output-on-failure
```

Цель `kratos_tests` — набор проверок на фикстурах (52 теста). Всё идёт через публичный C-интерфейс `api.h`, так же, как у приложения. Отдельные тесты можно запускать по части имени: `build/core/kratos_tests cancel`.

Набор проверяет, в частности:

- все фикстуры (ELF для ARM, ARM64, x86, x86-64; повреждённые, обрезанные, без секций, с обнулёнными секциями, с мусором в конце, с обфусцированными именами, с упакованными релокациями; APK с несколькими ABI, вложенными архивами, хранимыми записями, битым оглавлением и контрольными суммами, без библиотек) на ожидаемый итоговый статус;
- что итоговый статус совпадает со списком обязательных ошибок, а `summary.json` на диске совпадает с результатом запуска;
- наличие и непустоту всех обязательных отчётов;
- разрешение вызовов через PLT на ARM, ARM64 и x86-64, в том числе без таблицы секций и без символов;
- отметку подтверждённых и эвристических ссылок;
- пробелы анализа для повреждённых файлов (они должны быть записаны, а не скрыты);
- выбор библиотек в APK (автоматический и ручной), независимое продолжение остальных этапов после ошибки в одной библиотеке;
- метаданные IL2CPP: корректные, с неверной сигнатурой, неподдерживаемой версией, обрезанные;
- ограничения (`limits.*`: значение 0 означает отсутствие ограничения; отсечённое ограничением отмечается);
- что каждая настройка действительно читается кодом и влияет на результат;
- отмену запуска, недоступную папку результатов, одинаковый результат при повторных запусках, одновременные запуски;
- строки в UTF-8 (кириллица, CJK) и UTF-16 обоих порядков байт;
- Zstandard (метод 93 в записях APK, сжатые секции ELF), zlib (сжатые секции ELF; deflate в APK проверяют все фикстуры APK), сверку ELFIO на здоровых и повреждённых файлах;
- большой файл (32 МБ, порог `perf.large_file_mb = 1`): режим большого файла, полный hex-дамп без пользовательского ограничения, строки до последнего мегабайта и рост пиковой памяти намного меньше размера отчёта (проверка памяти пропускается под санитайзерами);
- сбой записи отчёта (размер файла ограничивается средствами ОС): оборванный файл удаляется, сбой записан как необязательный, остальные отчёты созданы, статус «Завершено с ошибкой»; при `out.partial_results = false` каталог неуспешного запуска не остаётся;
- заголовок PLT0 на четырёх архитектурах, отсутствие дублей в `methods.txt` и `offsets.h`.

Тот же набор под AddressSanitizer и UndefinedBehaviorSanitizer:

```
FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer"
cmake -S core -B build/asan -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DCMAKE_C_FLAGS="$FLAGS" -DCMAKE_CXX_FLAGS="$FLAGS" -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"
cmake --build build/asan
ASAN_OPTIONS=detect_leaks=0 ctest --test-dir build/asan --output-on-failure
```

Тест JNI-моста в настоящей JVM (грузит `libkratos_jni.so` и вызывает те же функции, что и приложение):

```
core/tests/jni/run_jni_test.sh
```

Проверка того, что объявления нативных функций совпадают в `Native.kt`, `kratos_jni.cpp` и тестовом двойнике `Native.java` (ошибка здесь проявилась бы на устройстве как `UnsatisfiedLinkError`):

```
python3 scripts/check_jni_names.py
```

Эта проверка входит в `ctest`.

## Консольная утилита

```
build/core/kratos_cli apk app.apk -o out/ --profile standard
build/core/kratos_cli lib libgame.so -o out/ --profile maximum --meta global-metadata.dat
build/core/kratos_cli schema          # все настройки в виде JSON
```

Параметры: `--profile quick|standard|detailed|maximum`, `--set ключ=значение` (можно повторять), `--config файл.json`, `--lib запись_APK` (можно повторять), `--meta запись|none|путь`, `--temp каталог`, `--quiet`. Результаты кладутся в `out/android_dump/<имя>_<дата>_<время>/`.

## Приложение для Android

```
./gradlew :app:assembleRelease
```

Результат — в `app/build/outputs/apk/release/`: `app-arm64-v8a-release.apk`, `app-armeabi-v7a-release.apk` и `app-universal-release.apk`. Нативная часть собирается для двух ABI (arm64-v8a и armeabi-v7a) со статическим `libc++` и выравниванием сегментов под страницы 16 КБ.

Подпись. Подписывающий ключ берётся только из переменных окружения, в репозитории его нет:

```
export KRATOS_KEYSTORE_PATH=/путь/к/kratos-release.jks
export KRATOS_KEYSTORE_PASSWORD=...
export KRATOS_KEY_ALIAS=...
export KRATOS_KEY_PASSWORD=...
```

Если все четыре переменные заданы и файл существует, релизная сборка подписывается этим ключом со схемами V1, V2 и V3. Иначе она подписывается отладочным ключом Android: такой APK устанавливается для проверки, но его нельзя распространять.

Проверка подписи собранного файла:

```
$ANDROID_HOME/build-tools/34.0.0/apksigner verify --verbose --print-certs app-arm64-v8a-release.apk
```

Обёртка Gradle (`gradlew`, `gradle/wrapper/`) создана командой `gradle wrapper --gradle-version 8.10.2`. Контрольная сумма дистрибутива в `gradle-wrapper.properties` не задана; при желании её можно добавить значением `distributionSha256Sum` с официальной страницы выпусков Gradle.

## GitHub Actions

Файл `.github/workflows/build.yml` содержит два задания.

1. `core-tests` — собирает ядро и запускает `ctest` в двух режимах (обычный и с AddressSanitizer и UBSan), а также тест JNI в JVM.
2. `android` — после успешных тестов ставит NDK и CMake через `sdkmanager`, собирает три APK, проверяет подпись `apksigner` и выкладывает файлы как артефакты сборки. В сводку задания попадают размер и SHA-256 каждого файла и результат проверки схем V1, V2 и V3.

Секреты репозитория (Settings → Secrets and variables → Actions):

| Секрет | Содержимое |
|---|---|
| `KRATOS_KEYSTORE_BASE64` | файл хранилища ключей в Base64 |
| `KRATOS_KEYSTORE_PASSWORD` | пароль хранилища |
| `KRATOS_KEY_ALIAS` | псевдоним ключа |
| `KRATOS_KEY_PASSWORD` | пароль ключа |

Создать хранилище и значение для первого секрета:

```
keytool -genkeypair -v -keystore kratos-release.jks -alias kratos -keyalg RSA -keysize 4096 -validity 10000
base64 -w0 kratos-release.jks
```

Ключ и пароли никогда не записываются в репозиторий и в файл workflow. Файл хранилища во время сборки лежит во временном каталоге раннера и удаляется в конце задания.

Если секретов нет (например, в запросах на слияние из форков, куда GitHub их не передаёт), сборка подписывается отладочным ключом, а артефакт называется `kratos-dump-apk-debug-signed`, и в именах файлов есть `-DEBUG-SIGNED`. Проверка «V1, V2 и V3 подписаны» в этом случае не требуется, а в сводке и в предупреждении задания сказано, что файлы нельзя распространять.

Задание `android` — единственный проверенный способ собрать APK без локального Android SDK: в среде, где писался проект, не было доступа к Google Maven и серверам Android SDK.

## Что проверено, а что нет

Проверено при разработке: сборка ядра и консольной утилиты на Linux (GCC 13), набор тестов (в обычной сборке и под AddressSanitizer и UBSan), тест JNI-моста в настоящей JVM, синтаксическая корректность файла workflow, компиляция всего Kotlin-кода против `android.jar` (API 34).

Не проверено: сама сборка APK (Gradle, Android Gradle Plugin, NDK-сборка для arm64-v8a и armeabi-v7a), установка и запуск приложения на устройстве или эмуляторе, работа системного выбора файлов, фоновой службы и уведомлений. Эти части написаны по документации и проверены только компиляцией Kotlin-кода; первый запуск задания `android` в GitHub Actions покажет возможные ошибки конфигурации сборки.
